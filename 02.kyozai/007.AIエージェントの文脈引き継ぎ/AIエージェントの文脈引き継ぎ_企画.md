# 教材企画: 新しいチャットで文脈が失われる問題と、その解決策

## 0. 前提

- **対象読者**: AIコーディングエージェント（Claude Code / Codex CLI / Cursor など）を日常的に使うエンジニア・技術寄りの実務者
- **想定レベル**: 中級。エージェントを使った経験はあるが、数日にまたがる作業を毎回ゼロから説明し直していて疲れている人
- **所要時間**: 約15分
- **ゴール（読了後にできるようになること）**
  1. 新しいチャットで文脈が消える理由と、長いチャットを続けても品質が落ちる理由を、コンテキストウィンドウの性質から説明できる
  2. 「毎回読ませる情報」「呼ばれたときだけ読む情報」「現在地のスナップショット」を区別して、置き場所を設計できる
  3. 引き継ぎメモに何を書き何を書かないかを判断でき、セッションの開始と終了に組み込める

**この教材で扱わないこと**: 特定ツールの設定手順、ベクトルDBやナレッジグラフを使った高度なメモリ基盤の実装。ここで扱うのは、プレーンなファイルだけで成立する設計の考え方。

---

## 1. 全体像 — セッションという箱の外に何を置くか

- **図解案**: 中央に「セッション（コンテキストウィンドウ）」の箱、その外に「ファイルシステム上の永続層」。セッションが終わると箱ごと消え、外に置いたものだけが次のセッションに引き継がれる、という構造図
- **伝えること**: エージェントはステートレス。会話は毎回まっさらから始まる。だから「覚えている」ように見せたいなら、外側に自分で置くしかない
- 本文で補う内容: 記憶があるように振る舞うのは、毎回ファイルを読み直しているから

## 2. なぜ消えるのか — 会話履歴は毎回まるごと送り直されている

- **図解案**: プロセスフロー。「ターン1: 履歴 [A] を送信」→「ターン2: 履歴 [A,B] を送信」→「ターン3: 履歴 [A,B,C] を送信」→「新セッション: 履歴 [] 」。送信量が右肩上がりに増え、最後に空に戻る
- **伝えること**: モデル側に状態は無い。毎ターン、それまでの全履歴を入力として渡し直している。だから履歴は積み上がり、セッションを閉じれば消える
- 本文: 「前回の話」を参照できたのは記憶ではなく、履歴が入力に入っていたから

## 3. 「じゃあ長く続ければいい」が成り立たない理由

- **図解案**: 折れ線／バー。入力長が増えるにつれて精度が落ちる曲線。「ウィンドウ上限」の縦線を右端に置き、劣化はそのずっと手前から始まることを示す
- **伝えること**: Chroma が18モデルを評価した Context Rot レポート（2025年7月）で、入力が長くなるだけで（タスクの難易度は一定なのに）性能が落ちることが全モデルで確認された
- 数字: 評価モデル18種（Claude 4系 / GPT-4.1系 / Gemini 2.5系 / Qwen3系）。「モデルはコンテキストを一様には使わない」
- クイズ1をこの直後に

## 4. 位置の問題 — 真ん中は読まれにくい

- **図解案**: 比率バー／位置別の精度。コンテキストの先頭・中間・末尾で正答率が変わるU字。先頭と末尾が高く中央が凹む
- **伝えること**: Lost in the Middle（TACL 2024）。関連情報が先頭か末尾にあるときが最も精度が高く、中央に置かれると大きく落ちる
- 数字: 20文書中、答えを1番目から10番目に動かすと正答率が30%以上低下
- 本文: 「入れておけば読まれる」は成り立たない。総量（3節）と位置（4節）の2つの別問題がある

## 5. 圧縮（compaction）は解決ではなく延命

- **図解案**: Before/After。左「長い履歴（発言・ツール出力・試行錯誤）」→ 右「要約された新しいウィンドウ」。要約の外にこぼれ落ちる小さな要素を描く
- **伝えること**: 上限に近づいた会話を要約して新しいウィンドウで再開する仕組み。設計判断・未解決のバグ・実装詳細を残し、冗長なツール出力を捨てる
- **限界**: 積極的に圧縮しすぎると、後になって初めて重要と分かる微妙な情報が失われる。圧縮は自動で、何を捨てたかは選べない
- 数字: Anthropic の Cookbook（2026年3月）の長時間リサーチ実験。約329,000トークンの文書群を扱わせたとき、コンテキスト管理なしのピークは335,279トークン、compaction を入れると169,164トークン、外部メモリを持たせた2回目のセッションは172,623トークンで再読み込みが4回減った
- 本文: だから「重要なものは自分で外に書く」が要る
- **図解案（差し替え）**: 4本のバーで「管理なし / 圧縮のみ / ツール結果の削除のみ / メモリあり(2回目)」のピークトークン数を比較

## 6. 記憶の3層 — 規約・手順・現在地

- **図解案**: 3層スタック。上から「規約（毎回読まれる）」「手順・スキル（呼ばれたときだけ読まれる）」「現在地スナップショット（セッション開始時に読まれる）」。右側に「読み込まれるタイミング」を注記
- **伝えること**: 性質の違う3つを1つのファイルに混ぜると破綻する。変わらない規約、必要時だけ要る手順、毎回変わる現在地は、更新頻度も読まれるタイミングも違う
- 本文: 3層に分ける基準は「いつ読まれてほしいか」

## 7. なぜ全部を毎回読ませないのか — 注意予算と just-in-time

- **図解案**: 2つのコンテキストウィンドウを対比。左「全部を先読み（規約＋手順＋過去ログ全部）で埋まった窓」、右「規約＋現在地だけ。残りは"パスだけ持つ"」
- **伝えること**: コンテキストは有限の注意予算。人間がすべてを暗記せずファイルシステムやブックマークで外部化するのと同じで、エージェントも識別子（ファイルパス）だけ持ち、必要になった時点で読む
- 本文: 「全部読ませておけば安心」は逆効果。3節・4節の劣化を自分で招く
- クイズ2をこの直後に

## 8. 引き継ぎメモに書くこと・書かないこと

- **図解案**: 2×2マトリクス。縦軸「次の判断に使うか」、横軸「再現できるか（コード・履歴を見れば分かるか）」。書くべきは「次の判断に使う × 再現できない」の象限
- **伝えること**: 書くのは、決定と**その理由**、却下した案とその理由、未解決の課題、次の一手。書かないのは、会話の逐語録、差分を見れば分かる変更内容、コードから読み取れる構造
- 本文: 理由が抜けた決定事項は、次のセッションで簡単にひっくり返される

## 9. スナップショットと履歴を分ける

- **図解案**: 対比図。左「スナップショット（現在地・1枚・上書きでよい）」、右「履歴（課題ログ・知見ログ・追記のみ）」。矢印で「解決した課題はスナップショットから履歴へ落とす」
- **伝えること**: 引き継ぎメモは履歴ではなく現在地。この区別が無いとメモが際限なく肥大し、3節の劣化を自分で作る
- 本文: 時系列で残したいものは別ファイルに追記する

## 10. 置き場所の標準 — AGENTS.md とツール固有ファイル

- **図解案**: 分解ツリー。「リポジトリ」→「AGENTS.md（ツール横断の標準）」「ツール固有の指示ファイル」「作業ログのディレクトリ」
- **伝えること**: AGENTS.md は2025年後半に策定されたエージェント向けの共通フォーマットで、6万を超えるリポジトリで採用され、Linux Foundation 傘下の Agentic AI Foundation が管理する。複数のツールを行き来するなら、規約はここに置くと二重管理を避けられる
- 本文: ツール固有ファイルは、そのツール専用の作法だけに絞る

## 11. 仕組みにする — 開始時に読ませ、終了前に書かせる

- **図解案**: ループ図。「セッション開始 → スナップショットを読む」→「作業」→「終了前にスナップショットを更新」→「次のセッション開始」。人間の記憶に依存する部分を最小化するのが狙い
- **伝えること**: 手動運用は必ず忘れる。開始時の自動読み込みと、終了前の書き出しを手順として固定する。書き出しは毎ターンではなく区切りで
- 本文: 書き忘れが常態化するなら、運用ではなく仕組みの側を直す
- クイズ3をこの直後に

## 12. 落とし穴

- **図解案**: 3枚カード相当の図。「肥大化」「秘匿情報の流出」「ファイル名でソート順が崩れる」
- **伝えること**:
  - 肥大化 — 追記しかしないメモは、いずれ読まれないコストになる。解決済みは履歴へ落とす
  - 秘匿情報 — メモは公開範囲を意識して書く。共有リポジトリに置くなら、認証情報・個人情報・生のアドレスを含めない
  - 日付だけのファイル名は1日に2回書くと上書きされる。時刻まで含めるか、命名規則のソート順を確認する
- クイズ4をこの直後に（3〜4問なのでここは任意 → 実装では3問に絞る）

## 13. 実装例 — 置き場所を決める

- **図解案**: ディレクトリツリーの左列と、「いつ読まれるか」の右列を並べた2カラム図
- **伝えること**: 規約はそのツールが読む規約ファイル（Claude Code なら `CLAUDE.md`、Codex CLI などは `AGENTS.md`）、手順は `.claude/skills/<名前>/SKILL.md`、フック定義は `.claude/settings.json`、現在地と履歴は `00.worklog/`（`handoff/` `issues/` `knowledge/` を1行ずつ図示）
- 本文: フォルダ名を `00.` で始めるのは一覧の先頭に固定するため。`issues/` `knowledge/` に索引を置くのが7節「パスだけ持つ」の実装
- **警告 callout**: スナップショットのファイル名は `YYYY-MM-DD-HHMM.md`。辞書順では `-` が `.` より前に来るので、`2026-08-11.md` は `2026-08-11-1428.md` より**後ろ**に並ぶ。時刻なしが1枚混ざると、そちらが「最新」と判定される

## 14. 実装例 — メモの見出しを固定する

- **図解案**: 8つの見出しを縦に積み、右側に各節の役割を注記。「決定事項と理由」「残作業」「次の最初の一手」の3つだけアクセント色
- **伝えること**: 見出しの固定で、書く側は迷わず、読む側は必要な節だけ拾える
- 本文: 「決定事項と、その理由」と「次に着手する最初の一手」を独立させる理由。「今後予定している作業」は見出しだけにする理由（着手するころには変わっている）

## 15. 実装例 — スキルとフックで自動化する

- **図解案**: 横軸の時間線。上のレーンにフック（SessionStart で読み込み）、下のレーンにスキル（終わりの合図で書き出し）
- **伝えること**: スキルの本文は使われたときにだけ読み込まれる（公式ドキュメントの記述を引用）。だから起動条件は description に書き、「今日はここまで」のような言い回しまで並べる。フックは `SessionStart` などのイベントに紐づける
- **表**: 規約ファイル／スキル／フックの「読み込まれるタイミング」と「向いている中身」
- **警告 callout**: 毎ターン走るイベントにリマインダーを仕込むとうるさくなる。まず description の拡充で足りるか試す
- クイズ4をこの直後に

## まとめカード（4枚）

1. **消えるのは仕様** — エージェントはステートレス。外に置いたものだけが残る
2. **長さは解決策ではない** — 総量でも位置でも精度は落ちる。入れる情報は選ぶ
3. **決定と理由と次の一手** — 再現できないものだけを、現在地として1枚に
4. **規約・スキル・フック** — 毎回読ませるもの、呼ばれたら読むもの、イベントで自動実行するもの
