# 教材企画: Macを持たないWindowsユーザーが、App Storeにアプリを出すまでの全ルート

## 0. 前提

- **対象読者**: **Macを一度も触ったことがないWindowsユーザー**。プログラミングは多少できるか、コードはAIコーディングエージェントに書かせる想定。iPhone は持っている（持っていない場合も後述の TestFlight で回る）
- **想定レベル**: 入門。**特許の章だけは知財の完全な素人**を想定し、法律用語は必ず言い換える
- **所要時間**: 約45分
- **手続きの前提**: Apple Developer Program は**成人本人**の契約。本人確認・銀行口座・米国税務フォームが要る（003 と同じ構造）
- **この教材のゴール（読了後にできるようになること）**
  1. 「Windowsで完結する範囲」と「macOSがどうしても要る範囲」を工程単位で線引きし、**自分に必要なMacの性能を作るアプリの種類から逆算**できる
  2. Macの調達方法4つを費用と手間で比較し、自分の本数に合う方法を選べる
  3. 登録・税務・審査・SDK期限に加えて、**特許を「とる／とらない」の判断を発売日より前に**下せる

- **意図的に外したこと**: Swift の書き方、UIデザイン論、Androidとの同時展開、法人設立の具体手続き、外国出願の実務
- **003（Steam版）との関係**: 「作る→登録→審査→公開→運営」という骨格は共通。**違いは2つ。** ①開発機のOSが指定される（macOSライセンス、クラウドMac、コード署名、SDK期限）②**知的財産の判断が発売前に必要**（Steam版では触れていない切り口）

## 1. 全体像 — 工程を「どのOSでやるか」で3レーンに分ける

- 図解案: **3レーンのスイムレーン図**。上から `Windows（あなたのPC）` / `macOS（借りるか買う）` / `Apple側（審査・配信）`。企画・実装・デバッグ・素材づくりは上レーン、署名とアーカイブとアップロードだけが真ん中レーン、審査と公開が下レーン
- 伝えること: **macOSレーンは全工程のうち細い1本でしかない**。「iOSアプリ＝Macが要る」は正しいが、「Macで全部やる」は誤り。この図が教材全体の地図になる
- 本文で補う内容: 誤解を先に潰す。Macが要るのは事実だが、要るのは終盤の一部だけ

## 2. Windowsだけで完結できるのか — 工程ごとの○×

- 図解案: **10工程の○×一覧表**。列は「工程」「Windowsだけでできるか」「できない場合の理由」
  | 工程 | Windowsだけ | |
  |---|---|---|
  | 企画・設計 | ○ | |
  | コードを書く（Flutter / RN / Unity） | ○ | |
  | Android実機・エミュレータで動作確認 | ○ | |
  | 画像・アイコン・スクショ素材づくり | ○ | |
  | Apple Developer Program の登録 | ○ | Webブラウザで完結 |
  | App Store Connect のメタデータ入力 | ○ | Webブラウザで完結 |
  | iOSシミュレータで動作確認 | **×** | シミュレータはXcode同梱 |
  | **コード署名** | **×** | `codesign` はXcode同梱 |
  | **アーカイブ（.ipa生成）** | **×** | `xcodebuild` はXcode同梱 |
  | **App Store Connect へのアップロード** | **×** | 署名済みビルドが前提 |
  | 審査対応（Resolution Center） | ○ | Webブラウザで完結 |
- 本文で補う内容:
  - **結論を先に言う。「アプリを作る」だけならWindowsで完結する。「App Storeに出す」なら完結しない。**
  - ×は4つだけ。しかもこの4つは連続した1本の作業で、慣れれば通しで30分〜1時間
  - 登録も税務もメタデータ入力も審査のやり取りも**全部ブラウザ**。Macが要るのは「ビルドを作って送る」瞬間だけ
- callout(key): 「Macを買うか」ではなく「**Xcodeを1時間だけどこで動かすか**」という問題に置き換わる

## 3. なぜその4工程だけmacOSなのか

- 図解案: **ビルドパイプラインの横フロー**。`コードを書く → コンパイル → コード署名 → アーカイブ → アップロード` の5箱を並べ、後半3箱を塗り分けて「Xcodeツールチェーン」の枠で囲む
- 本文で補う内容:
  - Xcode は macOS 専用。Windows版もLinux版も存在しない
  - iOSアプリは**署名されていないと実機でもストアでも動かない**。署名の `codesign`、提出形式（.ipa）を作る `xcodebuild` はどちらも Xcode 同梱
  - つまり「Macが要る」の正体は**Xcodeのツールチェーンが要る**ということ。ここを外せる抜け道はない
- callout: Flutter 公式のセットアップ手順にも「iOSビルドには macOS と Xcode が必要」と明記されている

## 4. やってはいけない回避策 — WindowsにmacOSを入れる

- 図解案: **左右対比**。左「許される（Apple製ハードウェア上での仮想化：追加2インスタンスまで）」／右「違反（非Apple製ハードウェアへのインストール・仮想化）」。中央に SLA の条文を短く引用
- 本文で補う内容:
  - macOS のソフトウェア使用許諾契約（SLA）は、インストール先を **Apple-branded computer** に限定している
  - 仮想化が認められるのは「すでに macOS が動いている Apple 製ハードウェア上」で、追加2インスタンスまで、用途はソフトウェア開発・テスト等。**PCの上のVMやHackintoshはこの例外に入らない**
  - 検索すると手順記事が出てくるが、契約違反であることは変わらない。Apple Developer Program という契約を並行して結ぶ立場では、リスクの取り方として釣り合わない
- callout(warn): 「動くかどうか」と「やっていいか」は別の話

## 5. Macの調達方法4つ — 費用と手間の比較

- 図解案: **4案の比較カード**（初期費用／継続費用／手間／向いている人）
  1. **実機を買う**（Mac mini 最小構成 **134,800円**／2026年6月24日改定。改定前は94,800円）
  2. **クラウドMacを時間で借りる**（MacinCloud Pay-as-You-Go：**$1/時〜、$4/日〜**、25時間または7日ぶんのプリペイド）
  3. **CIサービスにビルドさせる**（Codemagic / Expo EAS / GitHub Actions の macOSランナー。ビルド単位・分単位課金）
  4. **中古Mac**（初期費用は下がるが、後述のSDK必須期限に対応できる機種か要確認）
- 本文で補う内容: 年に1〜2本なら**時間課金が圧倒的に安い**。実例として、Unity製パズルゲームを個人リリースした開発者はクラウドMac利用**約15時間**で完了している。逆に週次でビルドを回すなら実機かCIに寄せたほうが総額もストレスも下がる
- callout: Mac mini は2026年6月に**4万円の値上げ**（94,800→134,800円）。「とりあえずMac買う」の判断コストが上がっているのが2026年の前提

## 6. どれだけの性能が要るか — 作るアプリのパターン別 ★新設

- 図解案: **4パターンの階段図**（左から右に必要スペックが上がる）。各段に「メモリ」「ストレージ」「クラウドMacで足りるか」を書く

  | パターン | 何を作るか | メモリ | ストレージ | クラウドMacで足りるか |
  |---|---|---|---|---|
  | **A. ビルド専用** | Flutter / RN / Unity を Windows で書き、Macはアーカイブだけ | 8GB可 | 借りる側の環境次第 | **◎ 最有力** |
  | **B. 素のネイティブ** | SwiftUIのユーティリティ、APIを叩くだけのアプリ | **16GB** | 512GB | ○（RAM選択できるプランで） |
  | **C. ゲーム・3D** | Unity / Unreal、アセットが重い | 24〜32GB | 1TB | △ 実機のほうが早い |
  | **D. 端末内ML・動画処理** | Core ML、映像エンコード、visionOS | 32GB〜 | 1TB〜 | × 実機推奨 |

- 本文で補う内容:
  - **全パターン共通の下限は「Xcode 26 が動くこと」。** Xcode 26 は macOS Sequoia 15.6 以降、26.4 以降は macOS Tahoe 26.2 以降が必要。macOS Tahoe のインストールだけで**35.5GBの空き**が要る
  - **16GBが実質的な基準線になった根拠**: Apple 自身が Xcode 16 の予測コード補完の動作要件に「Apple Silicon ＋ 16GB以上の統合メモリ」を指定した。8GBでは足りない領域があることを公式が示した形
  - ストレージは Xcode 本体だけで約20GB。これに DerivedData とシミュレータが積み上がるので、**256GBは数か月で枯渇する**。実機を買うなら512GB以上
  - **メモリもSSDも後から増やせない**（Apple Silicon は基板実装）。買うときに決め切る項目
  - **パターンAなら性能の議論そのものが不要になる。** これがWindowsユーザーにとって最も費用対効果が高いルート
- callout(key): 悩む前にまず「自分はパターンAでいけないか」を検討する。Aで済むならMacの性能表を読む必要がない

## 7. 何で作るか — Windowsで書けるフレームワーク

- 図解案: **4行の対応表**。列は「Windowsでコードが書けるか」「Windowsで動作確認できるか」「iOSビルドにmacOSが要るか」「上のどのパターンになるか」
  - Flutter / React Native（Expo） / Unity / ネイティブ（Swift・SwiftUI）
- 本文で補う内容:
  - **最終ビルドに macOS が要る点は全部同じ。** 違うのは「その手前をWindowsでどこまで進められるか」
  - クロスプラットフォーム系は Windows 上で書いて Android 実機やエミュレータで動作確認まで進められる＝パターンAに収まる
  - ネイティブSwiftを選ぶと**書く段階から macOS が要る**＝パターンB以上に上がり、クラウドMacの接続時間がそのまま膨らむ。Mac未経験者の1本目には向かない
- callout(key): 「どの言語が好きか」より「**macOSに触る時間を何分に抑えられるか**」で選ぶ

## 8. Apple Developer Program — 費用と、個人／組織の分かれ道

- 図解案: **分解ツリー**。共通（Apple Account＋2ファクタ認証／年会費 **99米ドル**）から、個人枝と組織枝に分岐
  - 個人: 法的な成人年齢／**正式な個人名**（屋号・ニックネーム・企業名は不可）／本人名義のクレジットカード
  - 組織: 法人格（屋号・商号・支店名は不可）／**D-U-N-S番号（必須・無料取得可）**／組織ドメインの仕事用メール／**公開されていて正常に動くWebサイト**
- 本文で補う内容:
  - 年会費は99米ドル（現地通貨の同等額）。日本円の請求額は為替で動くので、公式の米ドル表記を基準にする
  - **個人登録すると、App Storeの販売者名として本名が公開される。** ペンネームで出したいなら法人化が必要という構造
  - 組織はD-U-N-S取得とWebサイト用意で数日〜数週間かかる。**発売日から逆算して最初に着手する項目**
- callout(warn): 個人＝本名公開。後から変更が効かないので登録前に決める

## 9. お金を受け取る準備 — 順番を間違えると詰まる

- 図解案: **順序フロー（4ステップ）**＋各ステップに「これを飛ばすと何が起きるか」の注記
  `Legal Entity情報の更新 → 有料App契約への同意 → 銀行口座の登録 → 税務フォーム（W-8BEN）`
- 本文で補う内容:
  - この順序は固定。銀行口座を登録しないと税務情報の画面に進めない
  - **W-8BEN** は「米国居住者ではない」ことを申告して米国の30%源泉徴収を外すための書類。日本の個人事業主は W-8BEN-E ではなく **W-8BEN**（米国税法上、個人事業主は個人として扱われる）
  - 郵便番号は**ハイフン付き**（`100-0001`）でないと弾かれる、といった書式で足止めされやすい
  - 無料アプリだけなら有料App契約も銀行口座も不要。ただし**アプリ内課金を後から足すなら結局必要**になる
- callout: 003（Steam）のW-8BENと同じ論点。米国のプラットフォームで売る限り必ず出てくる

## 10. 手数料 — 30% / 15%、そして日本の「スマホ新法」

- 図解案: **比率バー3本**＋下に**タイムライン**
  - バー: 標準 **30%** ／ Small Business Program **15%** ／（EU代替規約の10%は参考表示）
  - タイムライン: 2025/12/18 スマホソフトウェア競争促進法 全面施行 → 外部決済への誘導が可能に → 2026年、外部決済の手数料水準に開発者から不満
- 本文で補う内容:
  - **Small Business Program は前暦年の全アプリ合計収益が100万米ドル以下なら対象**（新規デベロッパも対象）。**申請しないと適用されない**
  - 適用開始は「登録が承認された会計月の末日から15日後」。**自動では下がらないので、登録直後に申し込む**
  - 100万ドルを超えたらその年の残りは30%、翌年以降に下回れば再び15%に戻れる
  - 日本では2025年12月18日にスマホ新法が全面施行され、アプリ内から外部の決済ページへ誘導できるようになった。ただし外部決済にもApple側の手数料がかかり、**「30%が0%になる」わけではない**
- callout(warn): 15%は自動適用ではない。1本目を出す前に申し込む

## 11. 提出前に揃える技術要件 — 証明書・プライバシー・SDK期限

- 図解案: **3レイヤーのチェックリスト図**
  1. **署名まわり**: Apple Developer証明書 → App ID → プロビジョニングプロファイル
  2. **プライバシー**: `PrivacyInfo.xcprivacy`（プライバシーマニフェスト）＋ App Store Connect の App Privacy 申告
  3. **ビルド環境**: **2026年4月28日以降、Xcode 26 以降＋iOS 26 SDK でビルドしたものでないとアップロードできない**
- 本文で補う内容:
  - プライバシーマニフェストは2024年から必須。理由の申告が要るAPIを使っていると未対応で弾かれる。サードパーティSDKのマニフェストは自動でマージされる
  - **SDK必須期限はクラウドMac選びに直結する。** 借りたMacのXcodeが古いとアップロードで落ちる。契約前に「Xcodeのバージョンを選べるか／更新されるか」を確認する
  - 中古Macも同じ。**Xcode 26 が動くOSバージョンに上げられる機種か**が実質的な最低条件
- callout(key): Windowsユーザー特有の落とし穴は「自分のPCではなく借りたMacの環境が古い」パターン

## 12. TestFlight — Macも実機も持たない人ほど使う

- 図解案: **内部／外部の2列比較**
  - 内部: 最大**100人**（App Store Connect のロール保持者）／**審査なし**／即配布
  - 外部: 最大**10,000人**／**そのバージョンの最初のビルドだけ Beta App Review が要る**／メールやリンクで招待
- 本文で補う内容:
  - **クラウドMacにはiPhoneを物理接続できない。** Xcodeから実機を繋いでデバッグ、という定番の手が使えない
  - 代わりに TestFlight で自分のiPhoneに配って確認する。ログはXcodeのコンソールで拾えないので、**画面にログを出す仕組みをアプリ側に仕込んでおく**（実例でも同じ対処をしている）
  - 内部テストなら審査なしで即配れるので、確認サイクルは思ったより回る
- callout: 実機デバッグの前提が崩れる、というのがMac無し開発で一番効いてくる制約

## 13. 審査 — 期間と、リジェクトの三大理由

- 図解案: **横バー3本**（リジェクト理由の代表格）＋右上に「**90%が24時間以内にレビューされる**」のバッジ
  - **2.1 App Completeness** — 未解決の問題の**40%超**。クラッシュ・プレースホルダ・情報不足
  - **4.3 Spam** — 既存アプリの焼き直し・重複。2025〜2026年は**汎用AIチャットボット、AI画像生成クローン、AI要約、AIロゴ作成、AIコンパニオン、AI学習支援**が飽和カテゴリ扱い
  - **5.1.1 Data Collection** — 取得データの申告と実装の食い違い
- 本文で補う内容:
  - 平均は24時間以内だが、**新規アカウントの初回提出は2〜3日かかる**ことがある。発売日から逆算するときは初回だけ多めに見る
  - 4.3は「似ている」だけで飛んでくる。**何が既存と違うのかを審査メモに文章で書いて添える**のが実務上の対処
  - リジェクトは Resolution Center でやり取りする。感情的な反論ではなく、指摘番号に1つずつ答える
- callout(warn): AIを使ったアプリは2026年時点で4.3の警戒対象。「AIで作った」ではなく「何が新しいか」を書く

## 14. Windowsユーザーが実際に詰まる4か所

- 図解案: **失敗 → 対策の4行対比**
  1. **バージョン番号の不一致** → ビルド側とApp Store Connect側の番号を完全一致させる。上げ忘れが定番
  2. **`pod install` を忘れる** → ターミナル操作が要る。意味の分からないビルドエラーとして出るので原因に気づきにくい
  3. **実機ログが取れない** → 画面オーバーレイでログ表示、または TestFlight ＋ クラッシュログ
  4. **メタデータの変更にも新ビルドが要る** → アプリ名・キーワード・説明文・スクショの修正は溜めて一括提出
- 本文で補う内容: どれも「Macに繋いでいる時間が課金される」構造と噛み合って効いてくる。**Windows側で確定できることを全部確定させてからMacに繋ぐ**のが基本動作。実例では3回連続リジェクトを経験している
- 補足として、Mac未経験者が最初に戸惑う操作差（`Command`キー、Finder、キーチェーン、ターミナル）に1行触れる

## 15. Macに繋ぐ時間を最小化する設計

- 図解案: **ループ図**。`Windowsで実装・確認 → 変更をまとめる → Macでアーカイブ＆アップロード → TestFlightで確認 → Windowsへ戻る`。ループの中で**Macレーンの箱だけが課金対象**であることを色で示す
- 本文で補う内容:
  - 目標は「Macでやることをアーカイブとアップロードだけにする」。実例ではメタデータ修正を月1でまとめて接続時間を圧縮している
  - 次の段階は自動化。CIサービスや GitHub Actions の macOSランナーにビルドとTestFlight配信を任せれば、**手動でMacに繋ぐ時間をほぼゼロにできる**
  - 署名まわりは fastlane match（証明書とプロファイルを暗号化してプライベートGitに置く）が定番

## 16. 特許は取れるのか — 「アイデア」は特許にならない ★新設

> **この章の前提**: 知財の完全な素人向け。「発明」「新規性」といった言葉は必ず日常語に言い換える。断定的な法律アドバイスはせず、**判断の入口だけ**を渡す

- 図解案: **3段の判定フロー**（上から順に落ちていく形）
  1. `「〜できるアプリ」というアイデアそのもの` → **特許にならない**
  2. `画面の見た目・アイコンのデザイン` → 特許ではなく**意匠**の話
  3. `ソフトウェアがCPUやメモリを使って行う、具体的な処理の手順` → **ここだけが特許の土俵**
- 本文で補う内容:
  - 特許法でいう「発明」は、**自然法則を利用した技術的思想の創作**。単なる思いつきやビジネスのアイデアは含まれない
  - 特許庁の審査基準（附属書B 第1章 コンピュータソフトウエア関連発明）では、**ソフトウェアによる情報処理がハードウェア資源（CPU・メモリなど）を用いて具体的に実現されている**場合に限り「発明」に該当するとされている。逆に、そうでなければ発明ではない
  - だから「家計簿を自動で分類するアプリ」は特許にならない。「どういう手順で、どのデータを、どう処理して分類を実現するか」まで具体化して初めて土俵に乗る
  - **「うちのアプリのアイデアを盗まれる」という不安に、特許はほとんど答えてくれない。** 特許が守るのは仕組みであってアイデアではない
- callout: 「特許を取れるか」の前に「そもそも発明があるか」を確認する。ここで大半のアプリは対象外になる

## 17. 一番大事な落とし穴 — 公開したら原則アウト ★新設

- 図解案: **2本のタイムライン対比**
  - 上（正しい順）: `出願 → App Storeで公開` → 世界のどこでも取れる可能性が残る
  - 下（よくある順）: `App Storeで公開 → あとから出願` → **日本と米国は1年以内なら救済の可能性、欧州・中国は原則アウト**
- 本文で補う内容:
  - 特許は「まだ世に出ていないもの」にしか与えられない。公開してしまうと、**自分で公開した場合でも**原則として取れなくなる
  - 日本には救済制度がある（新規性喪失の例外・特許法30条）。公開から**1年以内**の出願で、かつ**出願と同時に申し出て、30日以内に証明書を出す**という手続きが要る。黙っていても適用されない
  - **App Store は世界配信。** リリースした瞬間に世界中に公開される。日本の例外規定で日本の特許は救えても、**欧州は原則グレースピリオドなし、中国も国際展覧会や指定学会など限られた場合のみ**。世界で権利化する道は事実上そこで閉じる
  - **TestFlightの外部テスト（最大10,000人）も「公開」とみなされうる。** 内部テスト（100人・関係者のみ）とはリスクが違う
- callout(warn): **特許を検討するなら、判断は「発売日の前」ではなく「テスト配布の前」**。順番を間違えると、あとから金額をいくら積んでも取り返せない

## 18. 特許・商標・著作権・意匠 — 個人開発者の現実解 ★新設

- 図解案: **4つの権利の比較表**（発生の仕方／費用／守れるもの／個人開発者への推奨度）

  | 権利 | どう手に入るか | 費用の目安 | 何を守るか |
  |---|---|---|---|
  | **著作権** | 書いた瞬間に**自動で発生**。手続き不要 | **0円** | 書いたコードそのもの（アイデアは守らない） |
  | **商標** | 出願して登録 | 1区分で**約44,900円**（出願12,000＋登録32,900、10年） | アプリ名・アイコン |
  | **意匠** | 出願して登録 | 出願・登録料が別途 | 画面デザイン。**2020年4月からGUI単独で登録可能**、存続25年 |
  | **特許** | 出願 → 審査請求 → 登録 | **特許庁だけで約17万円**＋弁理士**30〜60万円** | 具体的な処理の仕組み |

- 本文で補う内容:
  - 特許庁費用の内訳: 出願料 **14,000円**、出願審査請求料 **142,000円**（請求項1の場合）、特許料1〜3年分 **13,800円**。審査請求は**出願から3年以内**にしないと出願が取り下げ扱いになる
  - **中小企業・個人事業主は審査請求料と特許料が1/3に減免される**（2019年4月以降、証明書類の提出は不要）
  - **個人開発者にとって実害が出やすいのは特許ではなく商標。** アプリ名を他人に先に登録されると改名を迫られる。1区分44,900円は特許の1/10以下で、効き方も分かりやすい
  - **「とらない」も戦略。** 公開してしまえばそれが先行技術になり、同じものを他人が後から特許化することも難しくなる（防衛的公開）。1本目のアプリで数十万円と数年を特許に使う合理性は、多くの場合ない
- callout(key): 迷ったら優先順位は **①商標（名前）→ ②著作権（自動なので何もしない）→ ③意匠 → ④特許**
