# フラッシュ暗算ｘ履歴分析 要件定義

**ステータス: 実装済み（第5版）— 2026-08-12**

成果物: `フラッシュ暗算ｘ履歴分析_アプリ.html`（約3,660行・160KB・外部依存ゼロ）
最終更新: 2026-08-12

`03.apps/` の第1弾。教材（読む）に対する練習器具（やる）として、扉ページからバッジ付きでリンクする。

名前が示すとおり、**練習そのものと同じ比重で「履歴の分析」を主役に置く**アプリ。単発のスコアではなく、蓄積したプレイ記録から弱点を特定して次の練習を提案するところまでを範囲とする。

## 1. 位置づけと制約

### 1.1 このアプリが満たすもの

`02.kyozai/` の教材とは種別が違うため、不変条件を共通と種別ごとに分ける。

| 区分 | 条件 |
|---|---|
| **共通（絶対）** | 完全に自己完結（CDN・外部スクリプト・外部フォント・外部画像を一切読み込まない）。ライト／ダーク切替。オフラインでファイルを直接開いて成立する |
| **読む教材のみ** | 図解→本文の順、目次サイドバー、3択クイズ ← このアプリには適用しない |
| **練習アプリのみ** | 操作説明が初見で分かる。スマホでもPCでも完結して操作できる。記録は**端末内にのみ**保存し、外部送信は一切しない |

### 1.2 技術制約から来る帰結

- **グラフライブラリが使えない。** Chart.js / D3 は CDN 読み込みになるため不可。円・棒・折れ線はすべて **インライン SVG ＋ JS で自作**する
- **音声ファイルが使えない。** 効果音が要る場合は Web Audio API で合成する（**初期リリースは無音**。後から追加できる構造にしておく）
- **1ファイル完結を維持する。** 4,000行前後になる見込み

### 1.3 検証

`check_kyozai.py` は読む教材向け（文字数・図の点数・クイズ正解フラグ）なので、**このアプリは対象外**とする。CLAUDE.md にその旨を追記する。

代わりに確認すべきこと:

- 外部依存ゼロ（`http://` / `https://` を含む `src` / `href` が無い）
- SVG の色が `var(--*)` か `currentColor` になっている（16進ハードコードはダークモードで浮く）
- headless Chrome での実描画確認（日本語ラベルのはみ出しは実描画でしか分からない → know-0015）
- スマホ幅（375px）での表示確認

## 3. プレイヤー管理

- **最大4名**。名前は自由入力（全角10文字程度まで）
- プレイヤーごとに独立した履歴・ステージ進捗・自己ベスト・フリーモード設定を持つ
- 起動時に前回選択したプレイヤーを既定で選択状態にする
- プレイヤーの削除は確認ダイアログを出す（履歴も消えるため）
- **名前は端末内にのみ保存され、どこにも送信されない旨を画面に明記する**（公開ページなので、入力前に分かる位置に置く）

## 4. モード① ステップモード

### 4.1 構成

| コース | ステージ数 | 解放条件 |
|---|---|---|
| 初級 | 20 | 最初から |
| 中級 | 20 | 最初から |
| 上級 | 20 | 最初から |
| **超上級（隠し）** | 5 | **上級ステージ20を★★★（正答率100%）でクリア** |

コースごとに進捗を独立して持つ。超上級は解放されるまでコース選択画面に表示しない（解放時にアニメーション付きで出現させる）。

### 4.2 進行ルール（決定済み）

**順次解放＋クリア後は自由。** ステージNをクリアするとN+1が開く。一度クリアしたステージはいつでも再挑戦できる。

- **クリア条件: 正答率 80% 以上**（10問中8問正解）
- ステージ一覧では未解放を灰色、クリア済みに星を表示
- 星は3段階（80%＝★☆☆ / 90%＝★★☆ / 100%＝★★★）とし、再挑戦の動機を作る

### 4.3 ステージは後から追加できる（設計上の要点）

ステージ定義はコード内の**データ配列**として持ち、進捗は**配列インデックスではなくステージID**（例: `advanced-07`）をキーにしたオブジェクトで保存する。

これにより、**後からステージを増やしても既存プレイヤーの進捗が壊れない。** 途中に挿入することも、コースを追加することもできる。

## 6. モード③ 履歴分析モード

プレイ直後の結果画面が「今回の1回」を見るのに対し、こちらは**蓄積された全履歴**を見る。**このアプリの主役**。

### 6.1 期間の指定（第4版で拡充）

**目的は「自分の成長を見ること」**。そのため長期間の表示を制約しない。**既定は全期間**とする。

- **プリセット**: 直近7日 / 30日 / 90日 / 半年 / 1年 / **全期間（既定）**
- **カスタム範囲**: 開始日と終了日を指定できる（例: 2026年1月1日〜6月30日）。`<input type="date">` を2つ置く
- 読み込みは複合インデックス `[playerId+at]` の range クエリで行うため、期間を絞るほど速くなる（全件走査はしない）

### 6.2 集計粒度

1年分を日別で描くと365点が並び、スマホではつぶれて読めない。**期間に応じて粒度を自動で切り替える**（手動変更も可）。

| 期間 | 既定の粒度 | 点の数 |
|---|---|---|
| 〜90日 | 日別 | 最大90 |
| 90日〜1年 | 週別 | 最大52 |
| 1年超 | 月別 | 年12 |

日別は日々のブレが大きく傾向が見えにくいため、**長期の成長を見る目的には週別・月別の方が適している**。粒度を上げると各点のサンプル数が増え、線が安定する。

### 6.3 条件のそろえ方（第5版で追加）

フリーモードは設定を自由に変えられるため、**「まったく同じ条件」で絞ると比較対象が1〜2件しか残らない**。同一条件での比較だけでは成立しないので、粒度の違う4つの軸を用意する。

| # | 絞り方 | 比較対象 | 何が分かるか |
|---|---|---|---|
| ① | **すべて（既定）** | 全部 | **スコアの推移**。スコアは桁数×口数×速さで重み付け済みなので、条件が違っても大小に意味がある |
| ② | **難易度帯でまとめる** | 多い | 基礎配点を5段階（やさしい〜超難関）に丸める。設定が少し違っても同じ帯に入るので件数が稼げる |
| ③ | **軸を1つだけ見る** | 多い | 「口数7の問題だけ」を桁数・速度に関係なく集める。分析B（限界点の特定）がこれにあたる |
| ④ | **条件ぴったり** | 少ない | 純粋な同一条件。**5件未満のときは「参考値」と明示**し、断定的な文言を出さない |

**ステップモードは条件が固定**なので、ステージ単位で並べれば完全な同一条件比較になる（「初級12を5回」など）。

#### 1問あたりの点（条件をまたいで比較できる指標）

**セッションのスコア ÷ 問題数**を主指標のひとつに置く。

- 問題数の違い（5問と30問）に影響されない
- 難しい設定で正解するほど高くなる（配点が難易度で重み付けされているため）
- やさしい設定で満点をとっても、難しい設定で8割とるほうが高くなる

設定を変えながら遊んでも、**この数字が上がっていれば実力が上がっている**。条件のばらつきに強い指標として、上達曲線の主軸に使う。

### 6.4 表示内容

- 条件の絞り込み（モード、コース、難易度帯、桁数、口数、速度帯）
- **上達曲線**（既定は①スコアと到達難易度。②〜④は選択で切り替え）
- 累積プレイ数・累積問題数・総正答率などのサマリ
- 期間内の自己ベスト、期間の前半と後半の比較
- **JSON エクスポート／インポート**（→ §9.7）
- 記録が消える条件の説明（→ §9.8）

## 7. 出題ロジック

### 7.1 数の生成

1. 桁数範囲から各口の桁数をランダムに選ぶ
2. その桁数の範囲で数を生成（例: 2桁なら 10〜99）
3. 引き算ONなら、各口に確率 40% でマイナス符号を付ける（1口目は必ずプラス）
4. マイナス許容がOFFの場合、途中経過・最終結果が負になったらその口を再抽選する（10回試行して解決しなければプラスに固定）

### 7.2 表示

- 数字は画面中央に大きく表示。**背景色は変えず、数字だけを差し替える**（§12 参照）
- 表示間隔の間に空白フレームを入れる（既定 ON、設定で OFF 可）。空白なしは実際のフラッシュ暗算に近いが、連続する数字の切れ目が分かりにくくなる
- 開始前に「3・2・1」のカウントダウンを出す
- **各問の直前に「Ready」を1秒出し、だんだん薄くして消す。消えたら数字が始まる**（第6版で追加）。前の問題の判定表示から間を置かずに数字が出ると、身構える前に1口目が流れてしまうため。1問目もカウントダウンのあとに同じ合図をはさみ、「Ready が消えたら始まる」を全問で共通にする。動きを減らす設定（`prefers-reduced-motion`）のときは薄くせず1秒はっきり出す

### 7.3 出題の重複回避

同一セッション内で、まったく同じ数列は出さない。

## 8. 回答と採点

### 8.1 入力方式（第3版で確定）

**PC は物理キーボード、スマホ・タブレットは画面内テンキー。環境で自動的に出し分ける。**

スマホで `inputmode="numeric"` に頼ると、次の3つの問題が出る。

1. OS のテンキーに**マイナス記号がない**（マイナス許容設定で入力できない）
2. キーボードが**画面の半分を覆う**
3. 出たり消えたりで**レイアウトが動く**

そのため、タッチ環境では**自前のテンキー（0〜9・マイナス・削除・決定）を画面内に常設**し、入力欄は `readonly` にして OS キーボードを抑止する。

#### 判定と出し分け

| 環境 | 判定 | 画面内テンキー |
|---|---|---|
| スマホ・タブレット | `matchMedia('(pointer: coarse)')` が true | **常設表示** |
| PC | `matchMedia('(pointer: fine)')` が true かつ画面幅 ≥ 768px | 既定で非表示 |

- **設定で手動切替もできるようにする**（PC でもマウスで押したい場合、タッチ対応ノートPCなど、自動判定が外れる環境があるため）
- PC 側は**テンキー（`Numpad0`〜`Numpad9`）と数字キー行（`Digit0`〜`Digit9`）の両方**を受け付ける。テンキーのないノートPCがあるため
- マイナスは `-`（`Minus` / `NumpadSubtract`）、削除は BackSpace、決定は Enter（`NumpadEnter` 含む）

#### 共通

- **打ち直し（削除操作）の回数を計測する**（分析Dで使用）
- 回答時間は「表示終了時刻 → 決定時刻」で測る
- 入力がないまま一定時間（既定30秒）経過したら未入力として次へ進む

### 8.2 スコア（決定済み: 難易度✕正答＋速さボーナス）

```
1問の基礎配点 = 桁点 × (口数 / 3) × (1.0 / 表示間隔秒)

  桁点: 最大桁数が 1桁=10 / 2桁=20 / 3桁=35 / 4桁=55
       引き算ありは ×1.2、途中マイナス許容はさらに ×1.15

速さボーナス = 基礎配点 × b
  b = 0.2               （回答時間 ≤ 2.0秒）
  b = 0.2 × (4.0 - t) / 2.0  （2.0秒 < t < 4.0秒、線形に減衰）
  b = 0                 （回答時間 ≥ 4.0秒）

1問の獲得点 = 正答なら round(基礎配点 + 速さボーナス)、誤答は 0
セッションスコア = 全問の合計
```

- 結果画面には**スコアと正答率と平均時間を併記**する（スコアだけだと何が良かったのか分からないため）
- 自己ベストはモード・コース・ステージごと、およびフリーモードは設定条件ごとに保持

## 9. データモデルと永続性（★中核）

### 9.1 原則

**集計値ではなく1問ごとの生ログを保存する。** 出題された数の列と解答値さえ残っていれば、分析ロジックを後から書き直しても過去の全履歴に遡って再計算できる。**分析観点を後から追加できるのは、この設計があるからこそ。**

### 9.2 保存先: IndexedDB（第2版で変更）

当初 localStorage を想定していたが、履歴上限を **4名 × 10000セッション** とするため IndexedDB に変更する。

| | localStorage | IndexedDB |
|---|---|---|
| 容量上限 | 一般に約5MB | ディスク空き容量の数十%（実装依存） |
| 4名×10000セッション（約56MB） | **まったく収まらない** | 余裕 |
| Safari の7日ルール | 対象 | **同じく対象**（差はない） |

**永続性の面では両者に差がないため、容量だけを理由に IndexedDB を選ぶ。**

- DB名 `flashmental`、ストアは3つ
  - `players`（keyPath: `id`）
  - `sessions`（keyPath: `id`、index: `playerId`, `at`, `[playerId+at]`）
  - `summaries`（keyPath: `sessionId`、分析キャッシュ。→ §11.2）
- セッションを別ストアに分けることで、履歴が増えてもプレイヤー情報の読み書きが重くならない
- 期間で絞る分析は複合インデックス `[playerId+at]` の range クエリで読む（全件走査しない）
- IndexedDB が使えない環境では localStorage にフォールバックし、その場合は上限を100セッションに落として警告を出す

### 9.3 プレイヤーレコード

```jsonc
{
  "schemaVersion": 1,
  "id": "p1",
  "name": "たろう",
  "createdAt": "2026-08-12T10:00:00+09:00",
  "progress": {                        // ステージIDをキーにする（後から増やしても壊れない）
    "beginner-01": { "stars": 3, "bestScore": 420 },
    "beginner-02": { "stars": 2, "bestScore": 385 }
  },
  "unlocked": ["beginner", "intermediate", "advanced"],   // 超上級は条件達成で追加
  "freeSettings": { "digitMin":1, "digitMax":2, "terms":5, "interval":0.8,
                    "questions":10, "sub":false, "allowNegMid":false, "allowNegEnd":false },
  "best": { "free:1-2/5/0.8": 385 },
  "lastExportAt": "2026-08-12T20:00:00+09:00"
}
```

### 9.4 セッションレコード

```jsonc
{
  "id": "s1723420800000",
  "playerId": "p1",
  "at": "2026-08-12T19:00:00+09:00",
  "mode": "step",                   // "step" | "free"
  "stageId": "beginner-07",         // step のときのみ
  "cfg": { "digitMin":1, "digitMax":2, "terms":5, "interval":0.8,
           "sub":false, "allowNegMid":false, "allowNegEnd":false },
  "score": 420,
  "questions": [
    {
      "n": "12,-5,8,20,3",          // 出題された数の列（文字列で保持し容量を抑える）
      "a": 38,                      // 正解
      "u": 33,                      // 解答（未入力は null）
      "t": 2840,                    // 回答時間 ms
      "b": 1,                       // 打ち直し回数
      "p": 45                       // 獲得点
    }
  ]
}
```

**1問あたり約80バイト。** 平均15問のセッションで約1.4KB、**10000セッションで約14MB、4名で約56MB。** IndexedDB なら十分収まる。

### 9.5 履歴上限（第3版で変更）

- **プレイヤーごとに直近10000セッション。** 超えたら古いものから削除
- **自己ベストとステージ進捗はプレイヤーレコード側に持つ**ため、履歴が流れても記録は消えない
- 保存時に `navigator.storage.estimate()` で使用量を監視し、逼迫したら警告を出す
- 実運用では1人が10000セッションに到達するには相当な期間がかかる（1日10回でも約3年）。上限に当たることは事実上ないが、青天井にはしない

### 9.6 データはいつ消えるのか（重要）

**端末やブラウザの再起動では消えない。** ディスクに永続化されるため。消えるのは次の場合。

| 条件 | 結果 |
|---|---|
| 端末・ブラウザの再起動 | **消えない** |
| ブラウザの「閲覧データの削除（Cookieとサイトデータ）」 | 消える |
| プライベート／シークレットモード | ウィンドウを閉じると消える |
| **iOS / iPadOS の Safari で7日間サイトを開かない** | **消える** |
| ストレージ逼迫時の自動削除（eviction） | 消えることがある |
| 別デバイス・別ブラウザ | そもそも共有されない（同期しない） |

**iOS Safari の7日ルール** — Apple の ITP により、「7日間の Safari 使用のうち、そのサイトへのユーザー操作がなかった場合」に script-writable storage（localStorage・IndexedDB・Service Worker のキャッシュ等）が削除される。途中でアクセスすればタイマーは7日リセットされる。2026年時点でも有効。

出典: [WebKit — Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)

**ただし「ホーム画面に追加」した Web アプリは対象外。** Safari 本体とは別の使用日数カウンターを持ち、Apple 自身が「削除されることは想定していない」と明記している。

### 9.7 消えないための対策（要件）

1. **iOS/iPadOS で開かれたとき、「ホーム画面に追加」を案内するバナーを出す。** `<meta name="apple-mobile-web-app-capable">` `<meta name="apple-mobile-web-app-title">` `<link rel="apple-touch-icon" href="data:image/png;base64,...">` の3点で対応でき、**1ファイル完結を崩さない**（アイコンは data URI で埋め込む）
2. **`navigator.storage.persist()` を初回起動時に呼ぶ。** Chrome / Firefox のストレージ自動削除の対象外になる
3. **JSON エクスポート／インポート**
   - エクスポート: `Blob` ＋ `a[download]` で保存（外部通信なし）
   - インポート: `<input type="file">`。**既存データを置き換えるか統合するかを選ばせる**
   - `schemaVersion` が異なる場合は移行処理を通す（将来の拡張に備えた枠だけ用意）
4. **最終エクスポートから30日経過したら、バックアップを促すメッセージを出す**（`lastExportAt` で判定）

### 9.8 ユーザーへの案内（必須要件）

**記録が消える条件は、ユーザーに必ず伝える。** 黙って消えると履歴分析そのものが信用されなくなるため、次の3か所に置く。

| 場所 | 内容 | トーン |
|---|---|---|
| **プレイヤー作成時** | 「記録はこの端末のブラウザにだけ保存されます。他の端末とは共有されません」 | 短く1〜2行。作成の妨げにならない範囲 |
| **iOS / iPadOS の Safari で開いたとき（バナー）** | 「Safari では7日間開かないと記録が消えることがあります。**ホーム画面に追加**すると防げます」＋追加手順への導線 | 閉じられるが、再訪時に再表示（記録が消えるまで） |
| **履歴分析モード内の常設セクション** | §9.6 の表（消える条件の一覧）と、エクスポートによるバックアップの勧め | 折りたたみで常設。事実だけを淡々と |

- ホーム画面に追加済みで起動された場合（`navigator.standalone` や `display-mode: standalone` で判定）はバナーを出さない
- **不安を煽る書き方はしない。** 「消えることがある」「防ぐ方法がある」を並べて事実として書く

### 9.9 うまくいかなかったときの案内（第6版で追加）

**記録の読み書きに失敗しても、画面には何も出ないまま止まる** — これが実際に iPhone で起きた（10問目の直後と、分析を開いたときの2回）。原因が何であれ、**黙って固まったように見えることだけは避ける**。

- **失敗したら必ず画面に出す。** 閉じるまで残る帯（`#errbar`）で、何がうまくいかなかったかと「読み込みなおす」導線を添える。消えるトーストでは、固まったあとに気づけない
- **拾いきれなかったエラーも最後にここで受ける。** `window.onerror` と `unhandledrejection` を登録する
- **返ってこない場合にも備える。** 保存や読み込みは、失敗（例外）だけでなく**いつまでも返ってこない**ことがある。10秒の見張りを置き、超えたら同じ帯で案内する（待っている処理自体は止められないので、あくまで案内）
- **保存に失敗しても、結果画面は出す。** その回の結果はユーザーのものなので見せる。そのうえで「記録には残りません」と伝える

> 記録の書き込みが途中で止まると、生ログだけが残ってサマリが欠ける。すると次に分析を開いたとき §11.2 の再集計が走るため、**1つ目のつまずきが2つ目の症状を呼ぶ**。片方だけ直しても再発する。

## 10. 分析仕様（A〜F すべて採用）

### A. 誤答の原因分類 — 円グラフ

解答と正解の差から、何を間違えたかを推定する。**判定は上から順に評価し、最初に該当した分類を採用する**（特異なパターンを優先）。

`d = 解答 - 正解`、出題された数の列を `N` とする。

| 優先 | 分類 | 判定 | 意味 |
|---|---|---|---|
| 1 | **口の読み飛ばし** | `-d` が `N` のいずれかと一致 | その1口を見落とした |
| 2 | **符号の取り違え** | `d` が `N` のいずれかの `-2倍` と一致 | 引くべきを足した（逆も） |
| 3 | **桁上がりの落とし** | `\|d\|` が 10 または 100 の倍数（かつ 1〜2 に当たらない） | 繰り上がり・繰り下がりの処理漏れ |
| 4 | **数字の読み違い** | `\|d\|` が 9 の倍数で、かつ `\|d\| ≤ 90` | 12↔21 のような転置 |
| 5 | **微小誤差** | `\|d\| ≤ 3` | 単純な計算ミス |
| 6 | **崩壊** | `\|d\| > \|正解\| × 0.5` | 途中で追えなくなった |
| 7 | **未入力** | 解答が null | 時間切れ・断念 |
| 8 | **分類不能** | 上記のいずれにも該当しない | — |

- 円グラフは**今回のセッション**と**履歴全体**の2つを出す
- 各分類には短い解説文と、対策の一言を添える（例: 口の読み飛ばし →「口数を1つ減らして確実に追う練習を」）

> **この分類は後から改良できる。** §9 の生ログがあるため、ロジックを書き換えるだけで過去の全履歴が新しい基準で自動的に再分類される。分析観点の追加も同様。

### B. 限界点の特定 — 棒グラフ／ヒートマップ

- **桁数別・口数別・速度帯別の正答率**を棒グラフで表示
- 口数×速度の2軸ヒートマップ（セルの色の濃さ＝正答率）
- **「崩れ始める境界」を文章で名指しする**（例:「2桁×5口までは95%、7口で60%に落ちます」）
- サンプル数が少ない条件は「データ不足」と明示し、正答率を出さない（**最低5問**を閾値とする）

### C. セッション内の推移 — 折れ線

- 問題番号ごとの正誤（○×マーカー）と回答時間の折れ線を重ねる
- 前半／後半の正答率を比較し、**同じ正答率でも意味が違う**ことを示す（後半で落ちる＝持久力、前半が遅い＝ウォームアップ不足）

### D. 回答時間の分析

- 平均・中央値・標準偏差
- **正答時と誤答時の平均回答時間を比較** — 誤答が速いなら「見切り発車」、遅いなら「追えていない」
- 打ち直し回数の平均 — 自信のなさの指標
- 正答した問題の回答時間の分布（ヒストグラム）

### E. 時系列推移 — 折れ線

**成長を見るための中心的な分析。** 横軸の粒度は §6.2 に従って日別／週別／月別を切り替える。

- ベストスコアと平均スコアの推移
- 移動平均（単発のブレを均す。日別なら5回、週別・月別は粒度自体が平滑化されるため不要）
- **同一条件に絞った正答率の推移** ＝ 純粋な上達曲線
- 累積問題数と正答率の関係
- **期間の前半と後半を比較し、伸びを数値で示す**（例:「前半の平均 320点 → 後半 415点、+30%」）

### F. 文章レポート

上記の数値をテンプレートに差し込んで生成する。**診断だけで終わらせず、次にやるべき設定まで提案する。**

> 今回 17/20（85%）、スコア 420点。前回より +10pt。
> 誤答3問のうち2問が「1口読み飛ばし」で、いずれも7口以上の問題でした。
> 口数が増えたときの取りこぼしが課題です。
> **次は口数を7に固定し、表示間隔を0.8秒に落として練習することを勧めます。** ［この設定で始める］

- 履歴が3セッション未満のときは比較を伴う文言を出さない（誤った断定を避ける）
- 数値の根拠となる問題番号を併記し、結果画面から該当問題を振り返れるようにする

## 11. 分析観点は後から増やせる（設計方針）

### 11.1 原則

- 分析ロジックは**生ログを入力にとる純粋な関数群**として実装し、UI から切り離す
- 新しい観点を追加するときは関数を1つ足すだけで、**過去の全履歴に自動的に適用される**
- 分析結果を**恒久的な正データとしては保存しない**（保存すると、ロジック改良時に過去分と食い違う）

### 11.2 大量履歴でのパフォーマンス対策

上限を10000セッションにしたため、全期間分析では **15万問レコード**を扱うことになる。毎回すべて読んで集計すると数秒かかるので、次の3段構えにする。

**① グラフ描画には「サマリ」しか読まない（これが効く）**

グラフに必要なのは「その日のスコア」「正答数」「誤答の内訳」といった要約だけで、1問ごとの記録は要らない。

| | 1件のサイズ | 10000件の合計 | 読み込み＋集計 |
|---|---|---|---|
| 生ログ（`sessions`） | 約1.4KB | 14MB | 数秒 ← 重い |
| **サマリ（`summaries`）** | **約400バイト** | **4MB** | **1秒未満** |

**生ログを読むのは、特定のセッションを開いて1問ずつ振り返るときだけ**（1件1.4KBなので一瞬）。この分離により、**10000件・全期間が既定でも実用速度で表示できる。**

読み込みは複合インデックス `[playerId+at]` の range クエリで行い、全件走査はしない。期間を絞ればさらに速くなる。

**② 分析サマリをキャッシュする（`summaries` ストア）**

セッション終了時に、そのセッション分の集計（誤答分類の内訳、条件別の正誤数、時間統計）を計算して保存する。**`analysisVersion` を必ず添える。**

```jsonc
{ "sessionId": "s1723420800000", "playerId": "p1", "at": "...",
  "analysisVersion": 3,
  "errorTypes": { "skip": 2, "sign": 0, "carry": 1, ... },
  "byCondition": { "2d/7t/0.7s": { "ok": 5, "ng": 2 } },
  "timeStats": { "mean": 2840, "median": 2650, "sd": 610 } }
```

- 分析ロジックを改良したら `analysisVersion` を上げる
- 起動時にバージョン不一致を検出したら、**生ログから再計算してキャッシュを作り直す**（プログレス表示付き、バックグラウンドで実行）
- **キャッシュはあくまで導出物。正データは常に生ログ側**なので、§11.1 の原則は崩れない

**③ 再計算は分割実行する**

再計算はチャンク処理し、UI をブロックしない。件数が多い場合は「記録を再集計しています（1200 / 8500）」と進捗を出す。

**チャンクの合間に挟む待ちは `setTimeout(0)` にする。`requestIdleCallback` は使わない**（第6版で変更）。当初は `requestIdleCallback` を使っていたが、これは「ブラウザが暇になったら」であって、`timeout` を指定しても環境によっては何十秒も戻ってこない。**実測で headless Chrome が1回の待ちに59秒かかり、その間ずっと「記録を読み込んでいます…」の表示のまま**だった。ここで欲しいのは画面を描き直す隙だけなので、必ず短く返るほうを選ぶ。

> Web Worker を使えばさらに滑らかになる。1ファイル完結でも Blob URL 経由で Worker を生成できるため実現可能だが、初期リリースでは②③で足りると判断し、必要になってから導入する。

## 12. 安全性・アクセシビリティ

### 12.1 光過敏性発作への配慮

フラッシュ暗算は本質的に高速で表示を切り替えるため、設計で明示的に対処する。

- **背景の輝度を変えない。** 画面全体が白と黒を往復するような表示は使わず、**背景は固定して数字だけを差し替える**。WCAG 2.3.1 が問題にするのは大面積の輝度変化なので、この作りなら 6.7Hz でも基準の趣旨には反しない
- 起動時（プレイヤー選択画面）に注意文を出す
- 表示間隔の下限は **0.15秒**。それ以上速くはできないようにする
- 「空白フレームを入れる」を既定 ON にする（点滅感が下がる）

### 12.2 その他

- PC ではすべての操作をキーボードで完結できる（Tab / 数字 / Enter / Esc）
- スマホでは画面内テンキーで完結する（OS キーボードを出さない）
- Esc（またはヘッダーの中断ボタン）でいつでも中断してモード選択に戻れる
- 数字のコントラスト比を 4.5:1 以上に保つ（ライト・ダーク両方で検証）
- 数字の表示サイズを設定で変更できる（大・中・小）
